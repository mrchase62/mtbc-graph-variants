## P4P5-1: ABSENT is written at SNP sites where the matched reference only carries a different base (MEDIUM)

**Where:** `bin/p5_states.py:440-441`.

```python
elif pr is None or pr[1] != 0:
    state, allele = "ABSENT", ""
```

**What is wrong.** ABSENT is meant to say "this H37Rv position has no
equivalent in the sample's reference". But `odgi position -r R` reports
`dist.to.ref != 0` whenever H37Rv's base sits on a node that R does not walk.
That is true of **every SNP bubble where R carries the other base**, not only of
deletions. In the merged VCF, ABSENT becomes GT=2 against `*`, and the header
defines that as "Position deleted in this sample" (`merge_cohort_vcf.py:170-172`).

**Evidence.**

- Projection distances from the production store, at positions where R carries
  a biallelic SNP in the graph VCF (`distcheck.py`):

  | reference | dist 0 | dist 1 | dist >1 |
  |---|---:|---:|---:|
  | GCF_014900175 | 38 | 1,407 | 15 |
  | GCF_000016925 | 28 | 870 | 18 |
  | GCF_013010385 | 18 | 884 | 15 |

  So about 97% of R's own SNP positions read as "does not project".

- ABSENT cells at H37Rv-frame keys, classified by what the sample's reference
  carries at that base (`absentcheck.py`, over every sample):

  | | scale200 | gwas1000 |
  |---|---:|---:|
  | all H37Rv-frame ABSENT cells | 235,869 | 2,185,374 |
  | SNP key, R carries **the same ALT** | 8,790 | 70,358 |
  | SNP key, R carries a different base | 3,381 | 38,352 |
  | INDEL key, R carries a substitution at the anchor | 13,928 | 97,350 |
  | R really deletes the base (ABSENT is right) | 85,033 | 993,208 |

In the first two rows the position exists in R, so the cell is REF (the sample
reverted), ALT (a direct-arm miss) or another allele. It is never "deleted". The
matched gVCF at R's base could decide it, but that base is never consulted.

**Effect on current outputs.** In both cohorts' `merged.vcf.gz` and the states
array, about 12,000 (scale200) and 109,000 (gwas1000) SNP cells carry GT=2 where
the sample's own matched-frame data could give a genotype. By default,
`assoc/bin/write_event_matrix.py:227-238` reads GT=2 as unknown, so this costs
information rather than flipping genotypes. Tree or alignment builders that
treat `*` as a gap lose the same cells.

**Suggested fix.** Treat a small distance at a substitution as "projects". Keep
odgi's target position when `dist <= 1` and R's base there differs from H37Rv's
by substitution only (read both FASTAs), then run `ref_state()` at that target,
comparing the called base with the key's ALT as well as its REF. A shortcut is
to test the graph VCF: if R carries an ACGT substitution at the key position,
use the adjacent projected base. Write ABSENT only when R's path skips a run of
H37Rv bases, which is a real deletion.

## P4P5-2: Core keys are stated REF where the sample's own reference carries the ALT (MEDIUM)

**Where:** `bin/p5_states.py:448-450` with `ref_state` at `315-328`. The cause is
in `bin/p4_place.py:392`: the inherited half is kept only outside core
(`if region(pos) == "core" ... continue`).

**What is wrong.** In core sequence, ALT comes only from the direct arm
(P1 against H37Rv). With no direct-arm record, REF is earned from the
**matched** gVCF at the projected R position. When R itself carries the key's
allele, a reference block there means the sample matches R, so it carries the
ALT. Nothing checks whether R and H37Rv differ at the key.

**Evidence** (`refcheck.py`, all 200 scale200 samples). These are cells at core
keys whose allele the sample's reference carries in the graph VCF (normalised
identically), with the matched gVCF showing a GT=0 block of DP of at least 5 at
the projected base:

| key kind | cells stated REF | for comparison: ALT |
|---|---:|---:|
| SNP | 57 | 196,374 |
| INDEL < 50 bp | 414 | 15,493 |
| INDEL >= 50 bp | 618 | 1,401 |

That is **29% of the cells where the reference carries a core indel of at least
50 bp.**

Examples:

- SAMEA111556136 (reference GCF_014900175), `h37rv:1481337:G>A`, stated REF.
  The direct BAM pileup is about 50% A in a paralogous region, so GATK made no
  call. The matched frame shows the sample equal to R, which carries A.
- Same sample, `h37rv:2401825:T>T+116bp` (a 58 bp tandem unit, two copies
  added), stated REF. The direct arm cannot call a 116 bp insertion.

**Effect on current outputs.** About 1,090 scale200 cells. gwas1000 was not
counted (UNVERIFIED; expected roughly 5x). For the indels of 50 bp or more,
REF is right only if the sample lacks R's inserted sequence and GATK failed to
call that against R. The anchor-base evidence cannot rule that out, so those 618
are "unsupported REF" rather than proven wrong. The 471 SNP and short-indel
cells contradict the sample's own matched-frame call.

**Suggested fix.** Before returning REF for an H37Rv-frame key, check whether
the sample's reference carries the key's allele. That is a lookup of R's column
in `all_variants.nolab.vcf.gz`, normalised with `mtb_norm`, built once per
reference. If it does, state ALT (component `inherited`) when the gVCF block is
GT=0, and NOCALL otherwise. Equivalently, extend the inherited half in
`p4_place.py` to core keys that the direct arm did not call.

## P4P5-3: An inherited SV deletion is "confirmed" by one clip cluster even when the H37Rv frame shows full depth (MEDIUM)

**Where:** `bin/p5_sv_genotype.py:261-264`.

```python
if hs == "ALT" or hclips >= 1:
    return "ALT", f"{kind}_confirmed"
if hs == "REF":
    return "REF", f"{kind}_contradicted"
```

**What is wrong.** `h_clip_sides >= 1` (3 or more clipped reads within 25 bp of
either breakpoint, from `sv_twoframe.py:184-186`) promotes the candidate to ALT
**before** the H37Rv-frame state is examined. A sample whose H37Rv-frame depth
covers at least 80% of the interval (`h_state=REF`) is therefore promoted
whenever one end has a clip cluster, which is common in repeats and at IS6110
junctions. The `contradicted` branch is only reached when there are no clips.
The comment at `p5_sv_genotype.py:285-302` and `sv2frame/bin/sv_twoframe.py`'s
own `strong` rule both say a clip is supporting evidence, not a verdict.

**Evidence** (`tfcheck.py`: svgt_iv_states joined to the twoframe tables):

| cohort | confirmed ALT, total | H37Rv frame REF, clips >= 1 | H37Rv frame NOCALL, clips >= 1 |
|---|---:|---:|---:|
| scale200 | 6,943 | **995** | 923 |
| gwas1000 | 47,517 | **7,321** | 6,766 |

**Effect on current outputs.** In each cohort's merged VCF, CLASS=sv
COMPONENT=interval, those cells are GT=1. That is 995 of scale200's 15,168
interval ALT cells (6.6%), and about 7,300 in gwas1000.

**Suggested fix.** Test `hs == "REF"` first and return `contradicted`, or
NOCALL. Require `hs == "ALT"`, or `clips == 2` with ambiguous depth (the rule
`sv_twoframe` already uses for its own ALT), for a confirmation.

## P4P5-4: Caller SV records genotyped hom-ref (0/0) become ALT carriers (MEDIUM)

**Where:** `bin/p4b_place_sv.py:32-64` reads every record with an SVTYPE and
never looks at FORMAT/GT. `bin/p5_sv_matrix.py:251` filters on FILTER only.

**Evidence.** delly writes PASS records whose sample genotype is `0/0`
(scale200: 1,695 DEL and 1,082 DUP among the caller VCFs). Matching each kept
P4b row (PASS, DEL or INS, H37Rv frame, at most 100 kb) to its representative
caller record by coordinates (`svgt00.py`):

| cohort | DEL rows from a 0/0 record | DEL rows, non-ref GT | INS rows from a 0/0 record |
|---|---:|---:|---:|
| scale200 | 883 | 4,597 | 0 |
| gwas1000 | 6,604 | 28,821 | 1 |

**Effect on current outputs.** About 16% of the caller-half DEL rows in
`sv_matrix.tsv` carry an ALT cell for a sample its own caller called reference.
These cells reach:

- the UNCATALOGUED presence-only DEL records of the merged VCF (2,938 records
  in scale200, 10,518 in gwas1000; the overlap was not counted);
- catalogue admission (`n_alt >= 2` in `sv_intervals.py:163`), which only adds
  an interval to genotype and so is benign.

Catalogued deletions are genotyped by depth and are unaffected.

**Suggested fix.** In `parse_sv_vcf`, skip records whose GT has no non-zero
allele (`0/0`, `0`, `./.`), or carry GT into the row and filter it in
`p5_sv_matrix.py` next to FILTER.

## P4P5-5: Interval catalogue spans grow past the deletions they merge (MEDIUM)

**Where:** `bin/sv_intervals.py:120-138`.

**What is wrong.** Clustering compares each new deletion with the cluster's
current, already-widened `start` and `svlen`. On a hit it widens the cluster to
the union and resets `svlen` to the union span. Chains of overlapping deletions,
typically tandem repeats with different copy-number losses, therefore produce an
interval longer than most of its members. Every member's carriers are unioned
into `ref_carriers`.

**Evidence** (`ivdrift.py`, which reproduces the merge on
`all_variants.decomposed.vcf.gz`; 1,132 graph intervals, the same count as both
production catalogues):

- 278 intervals merge more than one distinct deletion. **125** of them span
  more than 1.5x their smallest member, which is the same-event length
  tolerance the docstring promises.
- Of 12,718 (interval, carrier reference) pairs, **1,120** have the reference's
  own deletion covering less than half of the interval.

Example: `svi:DEL:577323:174` and `svi:DEL:577439:58` sit in a 58 bp tandem
repeat. SAMEA1016021's reference carries a 116 bp loss (577381-577496). It is
listed as a carrier of the 174 bp interval, which comes back
`inherited_reference_unconfirmed` (NOCALL). The 58 bp interval comes back
`depth_present`, which is REF.

**Effect on current outputs.** The deletion block of both merged VCFs. Carriers
of a sub-deletion are tested against a longer interval: depth is partial, so
they come out NOCALL ("ambiguous depth"), and `PANELCARRIERS` overstates support.

**Suggested fix.** Cluster against a fixed representative (the first or the
modal member) and keep that member's coordinates. Never widen. If the union is
wanted for display, write it as separate columns that the genotyper does not
probe.

## P4P5-6: One insertion event appears as two or three records across arms (MEDIUM)

**Where:** `bin/merge_cohort_vcf.py`:

- caller SV rows at `822-854`;
- level-1 accessory presence at `872-910`;
- IS6110 at `912-949`.

No block deduplicates against another.

**Evidence** (`vcfdup.py`, `accsv.py`). In the merged VCFs:

- **Accessory presence and SV INS at the same POS.** An `acc:ACC_<pos>` record
  and an `sv:INS:<pos>:<len>` record share identical CHROM/POS/REF/ALT:
  - scale200: 328 pairs. 88 have carriers on both sides, and 41 of those have
    carrier sets with Jaccard of at least 0.5.
  - gwas1000: 411 / 135 / 39.
- **IS6110-length insertions in the SV block.** These are `sv:INS` records of
  1,340-1,370 bp, the IS6110 length. scale200 has 143, and 100 of them have an
  `is6110` record within 20 bp. gwas1000 has 207, with 148 near an `is6110`
  record.

**Effect on current outputs.** Association and parsimony consumers count these
events two or three times, inflating tests and homoplasy for exactly the
insertion classes. `sv_intervals.py:180-188` acknowledges the IS6110 case but
only flags it, and only for deletions.

**Suggested fix.**

- In the merge, drop or flag (`INFO/DUPOF=<id>`) caller INS rows lying within a
  few bp of an IS6110 key, or of an accessory locus, with a compatible length.
- Or exclude IS6110-length INS from `p5_sv_matrix.py`, since the IS6110 arm owns
  them.

## P4P5-7: Node-frame state tables and panel AF are not build-scoped and are not made by the chain (HIGH for the planned rebuild; no effect on current outputs)

**Where:**

- `bin/p5_states.py:182-194`: `--node-paths` and `--node-positions` default to
  `accessory/assets/node_paths.tsv` and `node_positions.tsv`, relative to the
  current directory.
- `bin/p5_merge.sh:285-288`: does not pass either option.
- `bin/p5_matrix.py:28-30` and `p5_sanity.py:74`: `--graph-vcf` defaults to
  `graphs/CX333.s10k.k23.K15/...`, and `p5_merge.sh --matrix` does not pass it.

**What is wrong.** Both node tables come from
`accessory/bin/node_path_membership.py`, which is run by hand (no chain script
calls it) on one GFA and restricted to a hand-made node list
(`nodeframe_nodes_union.txt`). Node ids are graph-specific. On a new graph:

- p5_states silently reads the old graph's membership and offsets. A node id
  that exists in both graphs gets ABSENT or REF from the wrong sequence.
- An id missing from the table gets NOCALL. The table is only reported when the
  whole file is absent (`p5_states.py:341-343`).
- `p5_matrix` computes `h37rv_minor` from the old graph's allele frequencies.

**Evidence.** Current coverage is complete: 0 of 11,533 (scale200) and 0 of
21,743 (gwas1000) node-frame keys are missing from `node_paths.tsv` (dated
2026-09-28), so current outputs are not affected. The risk is to the rerun on a
new graph (HANDOFF 0l).

**Suggested fix.**

- Move both tables under `${BUILD}/assets/`, generated by `p0_prepare.sh` from
  the build's own GFA over **all** nodes (or regenerate from the cohort's
  keys.tsv before `--states`).
- Pass them explicitly from `p5_merge.sh`, and make a key whose node is missing
  from the table fatal above a small fraction.
- Pass `--graph-vcf "$(dirname "$OG")/all_variants.nolab.vcf.gz"` to
  `p5_matrix.py` and `p5_sanity.py`.

## P4P5-8: Inherited alleles are kept where the sample's own call overlaps them at a different position (MEDIUM)

**Where:** `bin/p4_place.py:364` and `392`. The test is
`pos in called_at`: same H37Rv position only.

**What is wrong.** An inherited record (R's difference from H37Rv) is suppressed
only when a called record sits at exactly the same H37Rv position. When the
sample's own call against R overlaps the inherited allele from another anchor,
both are emitted. For example, a called deletion can remove the bases R's
inherited MNP describes. The sample is then stated ALT for an allele its own
reads replaced.

**Evidence** (`inhov.py`, scale200): 782 of 87,464 inherited records overlap a
composed called record at a different position.

Example, SAMEA1016021 (reference GCF_013010385), PE/PPE homopolymer at
976,890-976,902:

- called: `TGGG>T` at 976,895;
- inherited: `T>TTT` at 976,890 and `TTG>GGG` at 976,896.

The direct arm, which is not used there, called only `T>TG` at 976,897.

**Effect on current outputs.** About 0.9% of inherited cells in scale200. These
are in masked and PE/PPE sequence, which is already the least reliable class.

**Suggested fix.** Suppress an inherited record when its REF span overlaps the
REF span of any called record, using the interval test the module already has
(`make_in_spans`), not equality of positions.

## P4P5-9: Composition replaces R's REF with an equal-length slice of H37Rv, which is wrong for indels spanning R-specific sequence (LOW)

**Where:** `bin/p5_keys.py:71-74` and `bin/p5_states.py:279`:
`canon = h37[pos-1 : pos-1+len(ref)]`.

**Evidence** (`refdis.py`, scale200 P4 tables). 436 of 4,475 composed called
INDEL records have a REF that is not H37Rv's sequence at that span (29 with
even the anchor base differing). SNPs: 37 records, all with the anchor
differing.

For these records the composed key, H37Rv slice to the sample's ALT, describes
a different event from the one called. Example: `TGGG>T` against R becomes
`TTTG>T` against H37Rv. `p5_keys.py` only counts them (`ref_disagree`).

**Suggested fix.** Write NOCALL, or a flagged key, for a composed indel whose R
REF does not equal H37Rv's slice, instead of a composed allele. The alternative
is to compose through the graph: R's haplotype across the span, with the edit
applied, then normalised against H37Rv.

## P4P5-14: SV depth reads reference blocks inside a deletion GATK itself called (LOW)

**Where:** `bin/p5_sv_genotype.py:209` uses `load_gvcf_blocks`, which counts every
gVCF line. `p5_states.py` guards against this with `alt_spans`; this script does
not.

**Evidence.** In SAMEA1016081's gVCF, an 84 bp deletion is called at 843,010
(GT 1, AD 0,12). It is followed by GT=0 blocks *inside* the deleted span:
843,015-843,052 and 843,054-843,097, at DP 12-25 and GQ 0. Those probes count as
covered.

Effect (`svref_vs_small.py`): in scale200, only 10 interval cells are
`depth_present` REF while the same sample has a placed deletion of at least
40 bp covering the interval. Small now, but the mechanism is general for
deletions GATK can call.

**Fix:** build the coverage from GT=0 lines and drop positions inside
`alt_spans`, using `p5_states.load_gvcf`.

## P4P5-15: Documentation that the code contradicts (LOW)

- `p5_sv_genotype.py:366-368`: the `--deleted-frac` help says "reported, never
  promoted to ALT". The code at `:312-313` promotes it to ALT (`depth_absent`)
  when the flanks are covered.
- `p5_merge.sh:254-258` says keys with no projection are stated NOCALL by
  p5_states. They are stated ABSENT (`p5_states.py:440`).

  `off_path_near` cells are 95% ABSENT in both cohorts.
- `p4b_place_sv.py:247-249` justifies `has_child` by LV=0 parents duplicating
  LV=1 children. On this graph's nolab VCF, no LV=0 indel of 50 bp or more has
  a child, so the rule never fires. Its backward scan (`:275-281`) also stops at
  the first child that ends before `pos`, the same early-stop bug fixed in
  `p6_annotate.make_lookup`. It is latent.

## P4P5-16: Working-tree `sv_twoframe.sh` and `.py` are an older, unchecked copy (LOW)

The working tree's `sv2frame/bin/sv_twoframe.py` lacks the samtools exit-status
checks (`_finish`) that the repository copy gained in `deefef7` (CODE_REVIEW
5.6). Its `.sh` wrapper (working tree only) has three problems:

- its catalogue defaults to the shared, retired `refbias/assets/sv_intervals.tsv`;
- it skips on an existing output without a freshness test;
- its `--merge` globs every per-sample table.

Production does not run either file: p5_svgt calls the repository `.py`, and the
twoframe tables are dated 2026-10-01, after the commit. Anyone rerunning the
`.sh` by hand gets the old behaviour.

**Fix:** delete the working-tree copies, or replace the `.sh` with a pointer to
`p5_svgt.sh --twoframe`, as HANDOFF 6.5 already plans for `sv2frame/<cohort>/`.

## P4P5-17: Minor robustness items (LOW)

- `p5_merge.sh:224` passes the **panel-frame** anchor file as `--need` to
  `proj_store.py`, while the store is keyed on the **refs-frame** source position
  that `frame_convert from-panel` restores. These are equal only because H37Rv's
  panel offset is 0 (`graph_frame_offsets.tsv`). `p5_svgt.sh` passes the
  refs-frame list. This is latent if a new panel ever rotates H37Rv.
  **Fix:** pass `${PANEL}.raw`, the refs-frame list, to `missing` and `emit`.
- Many-to-one projection: 14 (sample, SNP position) pairs in scale200 have two
  different alleles placed for one haploid sample, and both keys are stated ALT.
  77 more are the same key from two R positions, collapsed by `setdefault`.
  These are harmless but not reported.
- `p5_matrix.py:83-103` stores the panel allele frequency per **position** as
  the maximum over all alleles. `h37rv_minor` then flags a rare allele at a
  position where another allele is common.
- `p5_sv_matrix.py:240-244` and `p4_summary.py:54-55` skip samples without a
  table and only print the fact. `p5_finish.sh` counts state files but not P4b
  tables. Every count matches the refmap today.
- Record contig order (lexicographic, `merge_cohort_vcf.py:951`) differs from
  header contig order (numeric, `:249`): 1,054 (scale200) and 1,938 (gwas1000)
  order inversions. Tools that require the header order, such as some
  `bcftools concat` and `merge` modes, may refuse.
  **Fix:** sort node contigs numerically in both places.

## Checked and found sound

- **Direct and matched input VCFs** (pattern 7). All 334,954 scale200 direct-arm
  records, and all matched-arm records (57,966 scale200, 355,796 gwas1000), are
  FILTER `.`, GT `1` and biallelic. `load_vcf` not reading GT is therefore safe

## Open questions (not settled)

1. **"other" ABSENT cells.** These are ABSENT cells where the graph VCF shows
   R with neither a substitution nor a deletion at the base: 19,818 core SNP
   cells in scale200 and 154,342 in gwas1000. They could be R genotyped `.` in
   nested records, complex alleles, or projection failures. UNVERIFIED.
2. **R-deleted positions projecting at distance 0.** About 40% of bases inside
   deletions R carries project into R with `dist 0` (`distcheck.py`: 330-377 per
   reference). Those keys can then be stated REF from a neighbouring base's
   depth. This may be tandem-repeat ambiguity in the graph. Not quantified at
   the cell level.
3. **Reverse-strand re-anchoring disagreements.** P4 logs (several generations
   mixed) report `reanchored_anchor_disagrees` for 795 of 4,709 reverse-strand
   indels re-anchored onto H37Rv. This suggests an off-by-some projection for
   those. It was not traced.
4. **Large R-carried core indels stated REF.** For the 618 such cells in
   P4P5-2, it is unknown how many are true losses of R's insertion that GATK did
   not call. This needs read-level checks.
5. **P4P5-2 in gwas1000.** Not counted, for time.
