# Audit: p0_p2 (build preparation, reference selection, calling, orchestration)

Date: 2026-10-05. Read-only audit; no jobs submitted. Scratch: `/tmp/claude-12043/audit_p0_p2/`
(`resel.py` re-runs P1 selection over all 997 gwas1000 isolates; `h37.py`, `dups.py`,

**Which copy runs in production.** Everything in this area runs from the repository:

The cohort registry, cohort tables, build directory and outputs are in the working tree

## P0P2-1 (HIGH, if the rerun reuses output roots): the P1 and P2 "already done" tests ignore the build and the chosen reference

- `bin/p1_select_reference.sh:110-112`, `bin/p2_call.sh:130-143` (repository copy, production)

**What is wrong.** P1 skips a sample when `<s>.candidates.tsv` and `<s>.h37rv.vcf.gz`
exist:

```bash
if [[ -s "${OUTDIR}/${SAMPLE}.candidates.tsv" && -s "${WORK}/${SAMPLE}.h37rv.vcf.gz" ]]; then
    echo "[P1] ${SAMPLE}: already done"; exit 0
```

P2 skips when `<s>.p2.done` exists. The marker holds only a date (`date -Is > "$DONE"`).
`_legacy_complete` also writes a fresh marker for any sample that has `vcf.gz` plus
`delly.vcf`. Neither test compares anything with the current build or the current
refmap row:

- The candidates come from `panel_snps.vcf.gz` of whichever build produced them.
- P2's outputs are aligned to whichever reference the refmap named then.

Output roots (`refbias/<cohort>/p1`, `/p2`) and work dirs (`refbias/work/<cohort>_p1`)
are per cohort, not per build. So rerunning `refbias_run.sh gwas1000` after
`MTB_BUILD_DIR` points at a new build does the following, with no error:

- P1 keeps the old-panel selection for every isolate.
- `p1_summary.py` rebuilds `refmap.tsv` from those stale candidates.
- P2 keeps the old-reference calls.

There is one exception. If the old REFID has no index in the new build, P2 fails with
"P0 asset missing", but only at P2. When the refmap changes, for example after a
`--tie-margin` change or a panel change, P2 still keeps calls made against the previous
reference.

**Evidence.**
- Every output already carries the information needed: the P1 H37Rv VCFs and P2 VCFs
  have `##MTB_graph_build=7713a8d71d8e`, and the HaplotypeCaller command line in the P2
  header names the reference FASTA.
- Current outputs are consistent. In gwas1000 (997) and scale200 (200), the reference in
  every P2 VCF's `##GATKCommandLine` equals the refmap reference (0 mismatches). Only one
  build exists.

**Effect on current outputs.** None. The risk is to the planned rebuild and rerun:
every cohort rerun in place would silently keep P1 and P2 from build 7713a8d71d8e.

**Suggested fix.**
- P1: skip only if the H37Rv VCF's `##MTB_graph_build` equals `BUILD_ID`, and write the
  build id into the candidates file, or a sidecar, and check it too.
- P2: write `BUILD_ID` and `REFID` into `<s>.p2.done`, and skip only when both match.
  `_legacy_complete` should read the reference from the VCF's GATKCommandLine and the
  build from its stamp before accepting.
- Alternatively, make output roots build-scoped (`refbias/<build>/<cohort>/...`).

## P0P2-2 (MEDIUM): build assets are symlinks to mutable files; the repeat mask changed after the manifest, and every VCF stamp records the old checksum

- `bin/p0_prepare.sh:290-322` (`step_assets`), `bin/p0_prepare.sh:348-385` (`step_manifest`),
  `bin/stamp_build_id.sh:113-115`; repository copy, production

**What is wrong.** `step_assets` links rather than copies:
`panel_snps.vcf.gz -> graphs/CX333.../snps.vcf.gz` and
`repeat_mask.bed -> data/annotation/H37Rv_repeat_mask.bed`. The comment says this is so
that "a changed input is detectable". Nothing ever checks, though:

- `manifest.done` is written once.
- `refbias_run.sh` and the passes never re-hash the assets against `manifest.tsv`.
- `stamp_build_id.sh` stamps `##MTB_p0_manifest_sha256` from the manifest file, not from
  the assets.

**Evidence** (re-hashing every manifest entry):

```
CHANGED: repeat_mask.bed  refbias/build/7713a8d71d8e/assets/repeat_mask.bed
CHANGED: build_info.tsv   (panel provenance lines added later; harmless)
```

The two masks:

| | manifest records | link now resolves to |
|---|---|---|
| file | (written Sep 17) | `data/annotation/H37Rv_repeat_mask.bed`, modified Sep 28 |
| size | 9,184 bytes | 26,704 bytes |
| sha256 | `93805ebb…`, which is `H37Rv_repeat_mask.named.bed` | different |
| intervals | 181, name-based | 395 (measured plus named) |

P4 and P4b read `${BUILD}/assets/repeat_mask.bed` (`p4_place.sh:69`,
`p4b_place_sv.sh:51`). The scale200 and gwas1000 P4, P4b and P5 outputs date from
2026-10-01, so they used the 395-interval mask. Every VCF stamped since then still
claims the 181-interval manifest.

Mask-dependent results from before and after Sep 28 differ under one build id. This
applies to pilot, scale100, l7 and any cohort whose P4 predates Sep 28. I did not check
those dates per cohort (UNVERIFIED which cohorts are affected).

**Effect on current outputs.**
- scale200 and gwas1000 used the intended, new mask, so their results are as designed.
- Their provenance is wrong, because the stamp names the old mask.
- Any comparison across cohorts run on either side of Sep 28 mixes masks.

**Suggested fix.**
- Copy the assets into the build (they are small), or hash every asset at each pass
  start and refuse on a mismatch with `manifest.tsv`.
- Rebuilding the mask should create a new build id, or at least a manifest generation
  that the stamp records.
- Re-run `--step manifest` now, so the record matches what was used.

## P0P2-3 (MEDIUM, for the rebuild): P0 takes `panel_snps.vcf.gz` from a hard-coded graph directory, independent of `OG`

- `bin/p0_prepare.sh:46-48`, repository copy

```bash
GRAPH_DIR="${GRAPH_DIR:-graphs/CX333.s10k.k23.K15}"
OG="${OG:-$(ls "${GRAPH_DIR}"/*.smooth.final.og 2>/dev/null | head -1)}"
PANEL_SNPS="${PANEL_SNPS:-${GRAPH_DIR}/snps.vcf.gz}"
```

**What is wrong.** Setting `OG=<new graph>` without `GRAPH_DIR` has two effects:

- It produces a new build id from the new graph's bytes.
- It links the old graph's SNP matrix as that build's `panel_snps.vcf.gz`.

Nothing checks that the VCF belongs to the graph. Its sample set is not compared with
`accessions.txt`, and its header records the source VCF path but nothing compares that
either. P1 would then select references by the old panel's genotypes, and could pick an
accession absent from the new build. That case fails at the `.bwt` check, but only per
sample.

**Effect on current outputs.** None: the one build was made with matching defaults.

**Suggested fix.**
- Derive `GRAPH_DIR` from `dirname "$OG"` when `OG` is given.
- In `step_assets`, refuse unless the VCF's sample columns plus H37Rv equal
  `accessions.txt`.
- Record `PANEL_SNPS` and its sha in `build_info.tsv`.

## P0P2-4 (MEDIUM, for the rebuild): the P1 tie-break silently depends on crossmaps outside the build

- `bin/p1_summary.py:91-94, 119-129, 148-154`; `bin/p1_select_reference.sh:90` passes no
  `--crossmap-dir`; repository copy, production

**What is wrong.** The rule "a tie within 5 SNPs goes to the reference with more IS6110
intervals" reads `is6110/assets/isclean_matched/<ref>.crossmap.tsv`. That is a fixed
working-tree directory, not part of the P0 build. A missing crossmap returns `""`, and
the tie-break is then skipped without a word (pattern 3). The intervals are a property
of the panel. With a new panel:

- genomes without crossmaps silently fall back to pure distance;
- genomes kept from the old panel use counts measured on the old assemblies.

**Evidence.** The tie-break decided **118 of 997** gwas1000 references and **28 of 200**
scale200 references (`tie_break` column of `refmap.tsv`). All 333 crossmaps exist today,
and no `ref_intervals` or `rank2_intervals` cell is blank.

**Effect on current outputs.** None today.

**Suggested fix.**
- Make the crossmaps (or a per-reference interval-count table) a P0 build asset.
- Pass `--crossmap-dir` explicitly.
- Exit nonzero when a top-two candidate has no crossmap, unless `--tie-margin 0`. This
  matches the "missing crossmap is fatal" rule already applied in P1i (CODE_REVIEW 4.10).

## P0P2-5 (LOW): selection distance ignores ALT identity, and split multi-allelic panel sites count against the matching genome

- `bin/t8_select_reference.py:43-51, 62-67`, repository copy, production

```python
pos_idx[int(f[1])] = len(rows)          # last row at a position wins
...
if len(f[3]) == 1 and len(f[4]) == 1 ...: called.add(int(f[1]))   # ALT base discarded
...
for p, i in pos_idx.items():
    if p in called: q[i] = 1
```

**What is wrong.** This is pattern 1 in the selector.

- `panel_snps.vcf.gz` is `norm -m -any` output, so a tri-allelic site is two biallelic
  rows at one POS.
- `pos_idx` keeps only the last row at a position, so an isolate's call sets `q = 1` on
  the last row only. Earlier rows at that position are scored as if the isolate were REF.
- The isolate's ALT base is never compared with the row's ALT.

At such a site, take an isolate carrying the first row's allele:

- a genome with the same allele scores **2** mismatches (it is 1 where q = 0, and 0
  where q = 1);
- a genome carrying the *other* ALT scores **0**.

**Evidence.**
- Panel: 75,268 biallelic SNV rows; 473 positions have two or more rows (481 extra rows).
  All 473 have *different* ALTs.
- There are 5,229 genome cells where the ALT lies only in a non-last row.
- Re-running selection with allele-aware, all-row matching on all 997 gwas1000 isolates
  (`resel.py`, stable sort):
  - every chosen distance drops by about 25-35;
  - rank 1 changes for **6/997**.
- After `p1_summary.py`'s tie-break, 4 of those 6 already end on the allele-aware choice.
  Two would change:
  - `SAMEA7527324`: GCF_977011615 → GCF_014900835;
  - `SAMN07660156`: GCF_014899625 → GCF_045348265.
- `resel.py` reproduces the production candidates exactly for 987/997. The other 10
  differ only in the order of candidates at equal distance.

**Effect on current outputs.** The matched reference for about 2 gwas1000 isolates; all
are near-ties.

**Suggested fix.** Key the panel matrix on `(pos, alt)`, store the isolate's ALT, and set
`q[i] = 1` only where both match. An isolate ALT matching neither row should count as a
mismatch against every genome's call there.

## P0P2-6 (LOW / open question): genomes with more missing panel genotypes look closer, and isolate no-calls count as REF

- `bin/t8_select_reference.py:51, 54-69`, repository copy, production

**What is wrong.**

- `d = ((G != q) & (G >= 0)).sum()` is a raw count over the sites each genome has
  genotyped. A genome with more `.` cells (nested LV=1 records it does not traverse,
  absent regions) has fewer chances to mismatch.
- On the isolate side, any panel site without a PASS SNV call is 0. That covers no
  coverage, a deletion, an indel or complex record at the site, and a site masked by
  nothing. CODE_REVIEW 6.11 already notes this second point, and it is unchanged.

**Evidence.**
- Comparable sites per genome range from 72,932 to 75,249 (median 74,418), from
  286,111 `.` cells over 16,531 records.
- Normalising the distance to mismatches per comparable site changes rank 1 for
  **17/997** gwas1000 isolates relative to the allele-aware count.
- Typical distances are 100-450, so a 2,300-site spread in denominators (about 3%) moves
  near-ties.

**Effect on current outputs.** Possibly a different near-equivalent reference for up to
about 17 of 997 isolates. Which metric is "right" is a design decision, so this is
reported, not asserted.

**Suggested fix.** Score over sites that both sides called:
- use the P1 GVCF, or a depth mask, for isolate coverage;
- report `d / n_compared` alongside `d`.
At minimum, record `n_compared` in the candidates file so the effect is visible.

## P0P2-7 (LOW / open question): H37Rv can never be chosen as a matched reference

- `bin/t8_select_reference.py:41` (samples are the VCF columns); the panel VCF is a
  `vg deconstruct` output with H37Rv as the reference path

**What is wrong.** `panel_snps.vcf.gz` has 332 sample columns; `accessions.txt` has 333.
The missing one is `GCF_000195955` (H37Rv), because it is the deconstruct reference path.
So an isolate closest to H37Rv gets the nearest *other* genome.

**Evidence** (`h37.py`, H37Rv distance = the isolate's calls at panel sites):
- gwas1000: 0/997 isolates are closer to H37Rv than to their chosen reference.
- scale200: **1/200**, `SAMEA7526648` (lineage 4.9): H37Rv at 42 against the chosen
  GCF_013267635 at 56.

**Effect.** One scale200 isolate. Cohorts rich in lineage 4.9 (`l49`) would be affected
more.

**Suggested fix.** Add an all-REF H37Rv column (no missing cells) to the matrix in
`t8_select_reference.py`, or document that H37Rv is deliberately excluded from the
matched arm.

## P0P2-9 (LOW): P0 `refs` step is still non-atomic, and `refs.done` ignores dictionary failures

- `bin/p0_prepare.sh:216, 234-250`

**What is wrong.**
- `[[ -s "$fa" ]] || zcat "$src" > "$fa"`: a task killed mid-write leaves a truncated
  FASTA that the next run accepts and indexes.
- `refs.done` is decided by counting `*.bwt` only, so a logged `dict_failed` still lets
  the step complete. P2 then fails per sample on the missing `.dict`.

CODE_REVIEW 6.5 listed the P0 half of this. The "fixed" table covers only the P1/P2
FASTQs and `.bwt` ordering, and the P0 lines are unchanged.

**Evidence.** The current build is complete: 333 FASTA, 333 `.bwt`, 333 `.dict`, no
leftover `*.bwaindex.*` files.

**Effect.** None now. This is a risk for the rebuild.

**Suggested fix.** `zcat > "$fa.tmp.$$" && mv`. Count `.dict` files too, and check
`refs.failures.tsv` is empty before marking done.

## P0P2-10 (LOW): the runner sizes P2+ arrays from the cohort table but indexes the refmap

- `bin/refbias_run.sh:124, 387`; `bin/p2_call.sh:94` (also p3, p4, p4b, p5, svgt,
  archive)

**What is wrong.** `N` counts cohort rows, while every pass from P2 onward reads row
`TASK_ID+1` of `REFMAP`. When P1 is part of the chain, `p1_summary.py` guarantees the
same rows. It is not checked when P1 is skipped, though:

- `--from p2`;
- pinned-reference cohorts such as `scale100_h37rv`, whose refmap is hand-made;
- a cohort table edited after P1.

If the refmap has more rows than `N`, the extra samples are silently never processed by
any array pass.

Separately, `--only p2,p1` submits P2 with no dependency on P1, because `JOB[p1]` is
empty when P2 is submitted.

**Suggested fix.**
- Before submitting, when `p1` is not in `RUN`, require that the refmap's sample column
  equals the cohort's, set and order.
- Sort `--only` lists into `ORDER` order.

## P0P2-12 (LOW): `archive_alignments.sh` can "verify" an archive when both reads fail

- `bin/archive_alignments.sh:112-135, 183`

**What is wrong.** `archive_one` is called as `archive_one … || rc=1`, which disables
`set -e` inside the function. So a failed `samtools view -C` is followed by `mv` and
`index` anyway.

Verification compares `c1/c2`, `r1/r2` and `h1/h2`. If samtools cannot read either file,
for example because the binary or the reference is unavailable, all six are the empty
string or the md5 of empty input. They compare equal, and with `ARCHIVE_DELETE_BAM=1`
the BAM is removed.

**Suggested fix.**
- Use `set -e` inside the function (or `|| return 1` on every command).
- Require `c1 > 0` and that `c1` is numeric before declaring a match.

## Checked and found sound

- **`refbias_run.sh` orchestration:**
  - afterok chain p1→p1sum→p2→p2sum→{p3,p4,p4b}; p5pre waits for p5states and p4b;
  - p5vcf waits for p5, p5svgt, p1is and p3acc;
  - an sbatch rejection aborts the chain (`$(submit …)` failure triggers `set -e` on the
    assignment);
  - the throttle is applied only to arrays;
  - blank or comment lines between rows are refused;
  - the build must be the single build with `manifest.done`, or explicit;
  - every per-cohort dir is exported;
  - `--status` patterns.
- **Task-to-row mapping:** `TASK_ID+1` skips the header in P1 (cohort) and P2 (refmap).
  The refmap preserves cohort order, because `p1_summary.py` iterates the cohort.
- **Cohort and CRAM tables:** for gwas1000, scale200, scale100 and l7, there are no
  duplicate sample keys, no blank lines, and every cohort sample is in its CRAM table.
  `awk … exit` takes the first match, but there is only one.
- **CRAM decoding:** `MTB_CRAM_REF` md5 equals the CRAM `@SQ M5`
  (`57b12ff2…`, NC_000962.3).
  - `samtools collate | fastq -n -0/-s /dev/null` keeps unmapped reads (37,185 for
    canettii) and drops secondary and supplementary records.
  - The CRAMs carry no duplicate flags; the pipeline does no dedup, and no document
    claims it does.
- **Coordinate frame for P1:**
  - `refs/GCF_000195955.fasta` is `NC_000962.3`, 4,411,532 bp, offset 0, `+` in
    `graph_frame_offsets.tsv`;
  - the panel matrix is on `GCF_000195955#1#NC_000962.3`;
  - both sides use 1-based VCF POS;
  - `t8` ignores CHROM, which is safe with one contig on each side.
- **Isolate H37Rv VCFs** (HaplotypeCaller `-ploidy 1`):
  - in sampled isolates every record is GT=1, with no multi-allelic records and every
    FILTER `.`, so the `f[6] in (".", "PASS")` filter drops nothing;
  - the haploid GT is never parsed by `t8`, which is correct for this caller.
- **VCF and GVCF agreement:** in 5 gwas1000 isolates, every VCF variant is also a
  non-REF GT in the GVCF. The GVCF has 0-4 extra low-QUAL ALT records, which become
  NOCALL rather than REF downstream (CODE_REVIEW 3.3 logic).
- **P2 reference:** the P2 VCF's reference equals the refmap reference for all 997
  gwas1000 and 200 scale200 isolates. Every P2 small VCF carries the build stamp.
- **Earlier fixes re-verified in code:**
  - CODE_REVIEW 6.4: `MTB_CRAM_REF` plus `mtb_require_cram_root`;
  - 6.5: atomic FASTQ, the `.p2.done` marker, dysgu failure fatal;
  - 6.6: `SIM_REQUIRE_FQ`;
  - 6.7 and 6.8: row count and build choice;
  - 6.10: summaries exit 2 on missing samples.
- **`mtb_norm.normalise`:** a fuzz test of 197,540 random deletions, insertions and MNPs
  with shared suffixes (`fuzz.py`) found 0 haplotype changes, 0 REF mismatches and 0
  non-leftmost indels.
- **`vcf_gate.sh` check 3** really fires: tested with bcftools 1.20 on a toy VCF with a
  wrong REF, and the `REF_MISMATCH` line is matched. Minor: check 1 parses `0/2` as 0, so
  it would miss a bad diploid GT. All production GTs are haploid.
- **`build_repeat_mask.py`:**
  - BED output is 0-based half-open from 0-based flag arrays.
  - Gene and element starts from 1-based sources are used as 0-based. That is an
    off-by-one of one base in gene extension and classification only, which is
    immaterial.
  - P0 links the mask rather than generating it (see P0P2-2).
- **Current build 7713a8d71d8e:** 333 refs, each with `.fai`, `.bwt` and `.dict`; the
  frames table is complete (110 accessions with a nonzero offset); `ancestral.done` is
  present.
- **`stamp_build_id.sh`** inserts before `#CHROM`, re-indexes, and is idempotent.
- **`sync_back.sh`:**
  - no `--delete`;
  - rsync failures other than code 24 abort, or set `SYNC_FAILED`;
  - a push failure exits nonzero;
  - `*.archive.cram` is included before the `*.cram` exclude.
- **`config/project_env.sh`:** the site file is sourced first and every `MTB_*` variable
  is exported. `MTB_THREADS` is inherited as 8 from the login node, but only
  `simulate_and_call.sh` reads it, and P1 has 8 CPUs while P2 sets it explicitly.
- **`archive_alignments.sh`** is only reachable via `--only archive`, outside the
  default chain. Nothing reads `P1WORK/<s>.h37rv.bam` after P1, so
  `ARCHIVE_DROP_UNUSED` is safe.
